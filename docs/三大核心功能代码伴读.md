## 2. 高并发秒杀怎样实现

一次秒杀不是直接执行 `INSERT`，而是经过下面这条链路：

```text
HTTP 请求
  -> SeckillRateLimitInterceptor：Redis 滑动窗口限流
  -> VoucherOrderServiceImpl.seckillVoucher：生成订单 ID
  -> seckill.lua：原子校验并预扣 Redis 库存
  -> SeckillMessagePublisher：发送 RabbitMQ 消息
  -> VoucherOrderConsumer：异步消费
  -> VoucherOrderServiceImpl.createVoucherOrder：事务扣 MySQL 库存并建单
  -> SeckillMessagePublisher：发送延迟关单消息
  -> 超时仍未支付：关闭订单并回补两端库存
```

### 2.1 秒杀券先写入 Redis

秒杀请求只访问 Redis 判断资格，因此必须先把库存和活动时间放入 Redis。

实现类：`src/main/java/com/hmdp/service/impl/VoucherServiceImpl.java`

```java
@Override
@Transactional
public void addSeckillVoucher(Voucher voucher) {
    // 1. 保存优惠券基础信息。
    save(voucher);

    // 2. 保存秒杀库存和活动时间到 MySQL。
    SeckillVoucher seckillVoucher = new SeckillVoucher();
    seckillVoucher.setVoucherId(voucher.getId());
    seckillVoucher.setStock(voucher.getStock());
    seckillVoucher.setBeginTime(voucher.getBeginTime());
    seckillVoucher.setEndTime(voucher.getEndTime());
    seckillVoucherService.save(seckillVoucher);

    // 3. 必须等数据库事务提交成功后，才初始化 Redis。
    // 如果事务回滚却提前写了 Redis，用户会抢到一张数据库中不存在的券。
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                stringRedisTemplate.opsForValue().set(
                    SECKILL_STOCK_KEY + voucher.getId(),
                    voucher.getStock().toString()
                );
                stringRedisTemplate.opsForValue().set(
                    SECKILL_BEGIN_TIME_KEY + voucher.getId(),
                    Long.toString(voucher.getBeginTime()
                        .atZone(ZoneId.systemDefault()).toInstant().toEpochMilli())
                );
                stringRedisTemplate.opsForValue().set(
                    SECKILL_END_TIME_KEY + voucher.getId(),
                    Long.toString(voucher.getEndTime()
                        .atZone(ZoneId.systemDefault()).toInstant().toEpochMilli())
                );
            }
        }
    );
}
```

最终得到三个 Key：

```text
seckill:stock:{voucherId}  -> 剩余库存
seckill:begin:{voucherId}  -> 开始时间的毫秒时间戳
seckill:end:{voucherId}    -> 结束时间的毫秒时间戳
```

旧数据由 `SeckillVoucherInitializer.initialize()` 在应用启动后补齐。库存使用 `setIfAbsent()`，是为了防止应用重启时拿 MySQL 初始库存覆盖 Redis 已经预扣后的实时库存。

```java
@Override
public boolean preHandle(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler) throws Exception {

    // 登录拦截器已经把当前用户保存到了 ThreadLocal。
    UserDTO user = UserHolder.getUser();
    if (user == null) {
        return true;
    }

    String voucherId = lastPathSegment(request.getRequestURI());
    SeckillProperties.RateLimit limit = properties.getRateLimit();

    // 同一个 Lua 同时维护两个 ZSET：
    // 1. 某张券的所有请求；2. 某用户对某张券的请求。
    Long result = stringRedisTemplate.execute(
        RATE_LIMIT_SCRIPT,
        Arrays.asList(
            "rate:seckill:global:" + voucherId,
            "rate:seckill:user:" + voucherId + ":" + user.getId()
        ),
        Long.toString(limit.getWindowMillis()),
        Integer.toString(limit.getGlobalRequests()),
        Integer.toString(limit.getUserRequests()),
        UUID.randomUUID().toString()
    );

    // 0 表示允许通过；1 表示总流量超限；2 表示单用户超限。
    if (result == null || result == 0L) {
        return true;
    }

    response.setStatus(429);
    String message = result == 2L
            ? "请求过于频繁，请稍后重试"
            : "秒杀人数过多，请稍后重试";
    response.getWriter().write(
        objectMapper.writeValueAsString(Result.fail(message))
    );
    return false;
}
```

Lua：`src/main/resources/seckill_rate_limit.lua`

```lua
-- Redis TIME 保证多个应用实例使用同一时钟。
local redisTime = redis.call('time')
local now = redisTime[1] * 1000 + math.floor(redisTime[2] / 1000)
local minScore = now - tonumber(ARGV[1])

-- 删除滑动窗口以外的旧请求。
redis.call('zremrangebyscore', KEYS[1], 0, minScore)
redis.call('zremrangebyscore', KEYS[2], 0, minScore)

-- 先判断单券总流量。
if redis.call('zcard', KEYS[1]) >= tonumber(ARGV[2]) then
    return 1
end

-- 再判断当前用户的流量。
if redis.call('zcard', KEYS[2]) >= tonumber(ARGV[3]) then
    return 2
end

-- 本次请求进入两个窗口，requestId 保证 ZSET member 唯一。
redis.call('zadd', KEYS[1], now, ARGV[4])
redis.call('zadd', KEYS[2], now, ARGV[4])

-- 窗口长期无人访问时自动清理整个 Key。
redis.call('pexpire', KEYS[1], tonumber(ARGV[1]) * 2)
redis.call('pexpire', KEYS[2], tonumber(ARGV[1]) * 2)
return 0
```

当前 `application.yaml` 的默认值是：1 秒窗口、单券最多 2000 次请求、单用户最多 5 次请求。这里的 2000 是限流阈值，不等于已经实测达到 2000 QPS。

```java
@Override
public Result seckillVoucher(Long voucherId) {
    Long userId = UserHolder.getUser().getId();

    // 1. 先生成全局订单 ID。
    // 后面的 Redis 预占、MQ 消息、MySQL 订单、状态查询都使用它串联。
    long orderId = redisIdWorker.nextId("order");

    // 2. 一次 Lua 原子完成资格判断和预占。
    Long result = stringRedisTemplate.execute(
        SECKILL_SCRIPT,
        Collections.emptyList(),
        voucherId.toString(),
        userId.toString(),
        Long.toString(orderId),
        Long.toString(seckillProperties.getPublishConfirmTimeoutMillis()),
        Long.toString(seckillProperties.getReservationTtlSeconds())
    );

    if (result == null) return Result.fail("秒杀失败，请稍后重试");
    if (result == 1L) return Result.fail("库存不足！");
    if (result == 2L) return Result.fail("不允许重复下单");
    if (result == 3L) return Result.fail("秒杀尚未开始");
    if (result == 4L) return Result.fail("秒杀已经结束");
    if (result == 5L) return Result.fail("秒杀信息未初始化，请稍后重试");

    // 3. Lua 成功后只构造消息，不在 HTTP 线程中操作 MySQL。
    VoucherOrder voucherOrder = new VoucherOrder();
    voucherOrder.setId(orderId);
    voucherOrder.setUserId(userId);
    voucherOrder.setVoucherId(voucherId);

    // 4. 发送失败也不直接丢弃资格，恢复任务会重投或补偿。
    try {
        seckillMessagePublisher.publishCreateOrder(voucherOrder);
    } catch (RuntimeException e) {
        log.error("首次发送秒杀订单消息失败，已进入自动恢复，orderId={}",
                  orderId, e);
    }

    // 5. 返回的是“已受理”的订单号，不代表 MySQL 已经创建成功。
    return Result.ok(orderId);
}
```

核心 Lua：`src/main/resources/seckill.lua`

```lua
local voucherId = ARGV[1]
local userId = ARGV[2]
local orderId = ARGV[3]
local confirmTimeoutMillis = tonumber(ARGV[4])
local reservationTtlSeconds = tonumber(ARGV[5])

local stockKey = 'seckill:stock:' .. voucherId
local orderKey = 'seckill:order:' .. voucherId
local beginTimeKey = 'seckill:begin:' .. voucherId
local endTimeKey = 'seckill:end:' .. voucherId
local reservationKey = 'seckill:reservation:' .. orderId
local pendingKey = 'seckill:publish:pending'

-- 1. 使用 Redis 服务器时间判断活动窗口。
local redisTime = redis.call('time')
local nowMillis = redisTime[1] * 1000 + math.floor(redisTime[2] / 1000)
local beginTime = tonumber(redis.call('get', beginTimeKey))
local endTime = tonumber(redis.call('get', endTimeKey))
if (not beginTime) or (not endTime) then return 5 end
if nowMillis < beginTime then return 3 end
if nowMillis > endTime then return 4 end

-- 2. 库存必须存在且大于 0。
local stock = tonumber(redis.call('get', stockKey))
if (not stock) or stock <= 0 then return 1 end

-- 3. Set 中已经有该 userId，说明该用户抢过此券。
if redis.call('sismember', orderKey, userId) == 1 then
    return 2
end

-- 4. 预扣 Redis 库存，并记录一人一单标记。
redis.call('incrby', stockKey, -1)
redis.call('sadd', orderKey, userId)

-- 5. 留下一份可恢复的资格预占记录。
-- 应用即使在发送 RabbitMQ 前宕机，后台任务仍能找到这笔订单。
redis.call('hset', reservationKey,
    'orderId', orderId,
    'voucherId', voucherId,
    'userId', userId,
    'status', 'PENDING',
    'attempts', '0')
redis.call('expire', reservationKey, reservationTtlSeconds)

-- 6. ZSET 的 score 是下一次检查是否需要重投的时间。
redis.call('zadd', pendingKey, nowMillis + confirmTimeoutMillis, orderId)
return 0
```

为什么一定要 Lua：库存判断、重复判断、扣库存、记录用户和写恢复记录必须是一个不可分割的 Redis 操作。否则线程可能都看到库存大于 0，随后一起扣减，或者只扣了库存却没有留下补偿依据。

### 2.4 第三关：RabbitMQ 异步创建订单

实现类：`src/main/java/com/hmdp/mq/SeckillMessagePublisher.java`

```java
public boolean publishCreateOrder(VoucherOrder order) {
    // 1. Redis 状态改成 PUBLISHING，attempts 加 1，加入待确认 ZSET。
    long attempt = reservationService.markPublishing(order.getId());
    if (attempt < 0) {
        // CREATED、COMPENSATED、CANCELLED 等终态不能再次发送。
        return false;
    }

    // 2. CorrelationData 让 Confirm 回调知道是哪一个业务订单。
    CorrelationData correlationData =
        new CorrelationData(EVENT_CREATE_ORDER + ":" + order.getId());

    try {
        rabbitTemplate.convertAndSend(
            RabbitMqConfig.SECKILL_ORDER_EXCHANGE,
            RabbitMqConfig.SECKILL_ORDER_ROUTING_KEY,
            order,
            message -> {
                // 消息持久化；还必须配合持久化交换机和持久化队列。
                message.getMessageProperties()
                       .setDeliveryMode(MessageDeliveryMode.PERSISTENT);
                message.getMessageProperties().setMessageId(order.getId().toString());
                message.getMessageProperties().setHeader(EVENT_TYPE_HEADER, EVENT_CREATE_ORDER);
                message.getMessageProperties().setHeader(ORDER_ID_HEADER, order.getId());
                message.getMessageProperties().setHeader("publishAttempt", attempt);
                return message;
            },
            correlationData
        );
        return true;
    } catch (AmqpException e) {
        // 本地发送异常写回 Redis，稍后由恢复任务重投。
        reservationService.markPublishFailed(
            order.getId(), "SEND_EXCEPTION:" + e.getMessage()
        );
        throw e;
    }
}
```

RabbitMQ 核心拓扑在 `RabbitMqConfig` 中：

```java
@Bean("seckillOrderExchange")
public DirectExchange seckillOrderExchange() {
    // durable=true：Broker 重启后交换机仍存在。
    return new DirectExchange(SECKILL_ORDER_EXCHANGE, true, false);
}

@Bean("seckillOrderQueue")
public Queue seckillOrderQueue() {
    // 创建订单消费失败并重试耗尽后，消息进入 DLX。
    return QueueBuilder.durable(SECKILL_ORDER_QUEUE)
            .deadLetterExchange(SECKILL_ORDER_DEAD_LETTER_EXCHANGE)
            .deadLetterRoutingKey(SECKILL_ORDER_DEAD_LETTER_ROUTING_KEY)
            .build();
}

@Bean
public Binding seckillOrderBinding(Queue queue, DirectExchange exchange) {
    return BindingBuilder.bind(queue)
            .to(exchange)
            .with(SECKILL_ORDER_ROUTING_KEY);
}
```

可靠发布不是只开“消息持久化”，而是四层组合：

1. 持久化交换机、持久化队列、持久化消息，降低 Broker 重启丢消息的风险。
2. Publisher Confirm 判断消息是否到达 Exchange。
3. Publisher Return 判断消息到达 Exchange 后是否无法路由到 Queue。
4. Redis 预占状态和恢复任务处理应用宕机、回调丢失和重复发送。

回调实现类：`src/main/java/com/hmdp/mq/RabbitMqProducerCallback.java`

```java
@Override
public void confirm(CorrelationData data, boolean ack, String cause) {
    if (data == null) return;
    // ACK：状态改为 PUBLISHED 并移出待恢复 ZSET。
    // NACK：状态改为 PUBLISH_FAILED，重新放入待恢复 ZSET。
    seckillMessagePublisher.handleConfirm(data, ack, cause);
}

@Override
public void returnedMessage(ReturnedMessage returned) {
    // Exchange 存在但 routing key 找不到队列时触发 Return。
    Object eventType = returned.getMessage().getMessageProperties()
                               .getHeaders().get("eventType");
    Object orderId = returned.getMessage().getMessageProperties()
                             .getHeaders().get("orderId");
    seckillMessagePublisher.handleReturned(
        eventType == null ? null : eventType.toString(),
        orderId == null ? null : Long.valueOf(orderId.toString()),
        returned.getReplyText()
    );
}
```

注意：Confirm ACK 只代表 Broker 接收了消息，不代表数据库订单创建成功。

### 2.5 第四关：消费者加锁、幂等建单

消费实现类：`src/main/java/com/hmdp/mq/VoucherOrderConsumer.java`

```java
@RabbitListener(queues = RabbitMqConfig.SECKILL_ORDER_QUEUE)
public void handleVoucherOrder(VoucherOrder order) {
    Long userId = order.getUserId();
    Long voucherId = order.getVoucherId();

    // 锁 1：同一 orderId 的建单、恢复、死信补偿不能并发。
    RLock lifecycleLock = redissonClient.getLock(
        "lock:seckill:lifecycle:" + order.getId()
    );
    if (!lifecycleLock.tryLock()) {
        // 抛异常让 RabbitMQ 重试，而不是无声丢弃消息。
        throw new IllegalStateException("未能获取订单生命周期锁");
    }

    // 锁 2：同一用户购买同一张券的操作串行。
    // 锁 Key 带 voucherId，不同券之间仍能并行。
    RLock userLock = redissonClient.getLock(
        "lock:order:" + userId + ":" + voucherId
    );
    boolean userLocked = false;
    try {
        SeckillReservation reservation = reservationService.find(order.getId());
        if (reservation == null) {
            throw new IllegalStateException("找不到秒杀资格预占");
        }

        // 迟到消息不能把已补偿或已取消的订单重新创建出来。
        if ("COMPENSATED".equals(reservation.getStatus())
                || "CANCELLED".equals(reservation.getStatus())) {
            return;
        }

        userLocked = userLock.tryLock();
        if (!userLocked) {
            throw new IllegalStateException("未能获取用户下单锁");
        }

        // 进入 Spring 事务方法，执行 MySQL 最终校验、扣库存和建单。
        SeckillOrderCreateResult result =
            voucherOrderService.createVoucherOrder(order);

        if (result == SeckillOrderCreateResult.CREATED
                || result == SeckillOrderCreateResult.IDEMPOTENT_SUCCESS) {
            reservationService.markCreated(order.getId());
            messagePublisher.publishOrderTimeout(order.getId());
            return;
        }

        // 永久业务失败不再重试，直接幂等归还 Redis 资格。
        reservationService.compensate(
            reservation,
            result.name(),
            result != SeckillOrderCreateResult.DUPLICATE_PURCHASE
        );
    } finally {
        if (userLocked && userLock.isHeldByCurrentThread()) userLock.unlock();
        if (lifecycleLock.isHeldByCurrentThread()) lifecycleLock.unlock();
    }
}
```

事务建单仍在 `VoucherOrderServiceImpl`：

```java
@Override
@Transactional
public SeckillOrderCreateResult createVoucherOrder(VoucherOrder order) {
    Long userId = order.getUserId();
    Long voucherId = order.getVoucherId();

    // 1. RabbitMQ 是至少一次投递，相同 orderId 再来一次要视为成功。
    if (getById(order.getId()) != null) {
        return SeckillOrderCreateResult.IDEMPOTENT_SUCCESS;
    }

    // 2. Redis 判断过一人一单，MySQL 仍要独立兜底。
    long count = query()
            .eq("voucher_id", voucherId)
            .eq("user_id", userId)
            .count();
    if (count > 0) {
        return SeckillOrderCreateResult.DUPLICATE_PURCHASE;
    }

    // 3. SQL 最终形态相当于：
    // UPDATE tb_seckill_voucher
    // SET stock = stock - 1
    // WHERE voucher_id = ? AND stock > 0;
    // stock > 0 是数据库层防超卖的最后一道条件。
    boolean success = seckillVoucherService.update()
            .setSql("stock = stock - 1")
            .eq("voucher_id", voucherId)
            .gt("stock", 0)
            .update();
    if (!success) {
        return SeckillOrderCreateResult.DB_OUT_OF_STOCK;
    }

    // 4. 扣库存和保存订单处于同一 MySQL 事务。
    if (!save(order)) {
        throw new IllegalStateException("订单保存失败");
    }
    return SeckillOrderCreateResult.CREATED;
}
```

数据库还存在最终唯一约束，定义于 `src/main/resources/db/hmdp.sql`：

```sql
UNIQUE INDEX `uk_voucher_user` (`voucher_id`, `user_id`) USING BTREE
```

因此“一人一单”一共有四道防线：

1. `seckill.lua` 的 Redis Set 快速拒绝。
2. Redisson 用户券锁减少同一用户并发竞争。
3. 创建订单前查询 MySQL。
4. `(voucher_id, user_id)` 唯一索引提供最终硬约束。

防超卖则主要依靠：Lua 原子预扣 Redis 库存，以及 MySQL 更新语句的 `stock > 0` 条件。用户锁不是防所有用户共同超卖的商品锁。

### 2.6 Redis、RabbitMQ、MySQL 之间怎样补偿

三个组件无法被一个本地事务同时提交，所以项目把每笔资格保存成状态机：

```text
PENDING
  -> PUBLISHING
  -> PUBLISHED
  -> CREATED

发送失败：PUBLISHING -> PUBLISH_FAILED -> 再次 PUBLISHING
最终建单失败：PENDING/PUBLISHING/PUBLISH_FAILED/PUBLISHED -> COMPENSATED
订单超时：CREATED -> CANCELLED
```

状态实现类是 `SeckillReservationService`，每次状态变化都调用独立 Lua。例如最终补偿的 `seckill_compensate.lua`：

```lua
local status = redis.call('hget', KEYS[1], 'status')
if not status then return 0 end

-- 已补偿、已取消或已经建单时不能再次加库存。
if status == 'COMPENSATED' or status == 'CANCELLED'
        or status == 'CREATED' then
    return 0
end

-- 归还库存。
redis.call('incrby', KEYS[2], 1)

-- 删除一人一单标记，让用户可以重新抢购。
-- 若数据库已经有同用户同券的另一订单，则传 0，不能删除该标记。
if ARGV[5] == '1' then
    redis.call('srem', KEYS[3], ARGV[2])
end

redis.call('hset', KEYS[1],
    'status', 'COMPENSATED',
    'reason', ARGV[3])
redis.call('expire', KEYS[1], ARGV[4])
redis.call('zrem', KEYS[4], ARGV[1])
return 1
```

恢复实现类：`src/main/java/com/hmdp/mq/SeckillPublishRecoveryJob.java`

```java
@Scheduled(fixedDelayString =
    "${hmdp.seckill.recovery-fixed-delay-millis:3000}")
public void recoverUnconfirmedMessages() {
    // 从 seckill:publish:pending 中取已经到检查时间的 orderId。
    for (String id : reservationService.findDueOrderIds(
            properties.getRecoveryBatchSize())) {
        recoverOne(Long.valueOf(id));
    }
}

private void recoverOne(Long orderId) {
    // 多实例恢复任务和消费者共用同一把生命周期锁。
    RLock lock = redissonClient.getLock(
        "lock:seckill:lifecycle:" + orderId
    );
    if (!lock.tryLock()) return;

    try {
        SeckillReservation reservation = reservationService.find(orderId);
        if (reservation == null || isFinished(reservation.getStatus())) {
            reservationService.removePending(orderId);
            return;
        }

        // 数据库已有订单，说明业务已成功，绝对不能补库存。
        if (voucherOrderService.getById(orderId) != null) {
            reservationService.markCreated(orderId);
            messagePublisher.publishOrderTimeout(orderId);
            return;
        }

        // 达到最大次数仍无法发布，才执行幂等补偿。
        if (reservation.getAttempts() >= properties.getPublishMaxAttempts()) {
            reservationService.compensate(
                reservation, "PUBLISH_RETRY_EXHAUSTED"
            );
            return;
        }

        // 未达上限，使用原 orderId 重发；重复消息由消费者幂等处理。
        VoucherOrder order = new VoucherOrder();
        order.setId(orderId);
        order.setUserId(reservation.getUserId());
        order.setVoucherId(reservation.getVoucherId());
        messagePublisher.publishCreateOrder(order);
    } finally {
        if (lock.isHeldByCurrentThread()) lock.unlock();
    }
}
```

若消息已经进入业务队列但消费连续失败，RabbitMQ 会把它投递到 `seckill.order.dlq`。`VoucherOrderDeadLetterConsumer` 仍然先按 `orderId` 查询数据库：数据库已有订单就按幂等成功处理；确实没有订单才补偿 Redis。这样可防止“数据库已提交、消费者 ACK 前宕机”导致错误加回库存。

### 2.7 超时订单自动关单并回补库存

数据库订单创建后，消费者调用：

```java
reservationService.markCreated(order.getId());
messagePublisher.publishOrderTimeout(order.getId());
```

延迟消息实现：

```java
public void publishOrderTimeout(Long orderId) {
    rabbitTemplate.convertAndSend(
        RabbitMqConfig.SECKILL_ORDER_EXCHANGE,
        RabbitMqConfig.SECKILL_ORDER_DELAY_ROUTING_KEY,

```

`seckill.order.delay.queue` 没有消费者；TTL 到期后，RabbitMQ 把消息作为死信路由到 `seckill.order.close.queue`，再由 `VoucherOrderTimeoutConsumer` 调用 `OrderTimeoutProcessor.process(orderId)`。

MySQL 关单核心代码：

```java
@Transactional
public boolean closeUnpaidOrder(Long orderId) {
    VoucherOrder order = getById(orderId);
    if (order == null) return false;
    if (Integer.valueOf(4).equals(order.getStatus())) return true;
    if (!Integer.valueOf(1).equals(order.getStatus())) return false;

    // 支付和关单都要求旧状态为 1，所以并发时最多成功一个。
    boolean changed = update()
            .set("status", 4)
            .eq("id", orderId)
            .eq("status", 1)
            .update();
    if (!changed) return false;

    // 订单状态与 MySQL 库存回补在同一事务中。
    boolean restored = seckillVoucherService.update()
            .setSql("stock = stock + 1")
            .eq("voucher_id", order.getVoucherId())
            .update();
    if (!restored) throw new IllegalStateException("回补库存失败");
    return true;
}
```

数据库事务成功后，`OrderTimeoutProcessor` 调用 `reservationService.cancelCreatedOrder()`，由 `seckill_cancel.lua` 把 Redis 状态从 `CREATED` 原子改成 `CANCELLED`，同时 Redis 库存加一、移除用户购买标记。重复超时消息因状态已经是 `CANCELLED`，不会重复加库存。

另外还有 `OrderTimeoutFallbackJob` 每分钟扫描数据库中的过期未支付订单，防止 RabbitMQ 延迟消息发送失败后订单永远占库存。

## 3. Caffeine + Redis 多级缓存怎样实现

店铺查询的真实顺序是：

```text
Caffeine L1
  -> BloomFilter
  -> Redis L2
  -> Redis 数据未逻辑过期：直接返回
  -> Redis 数据逻辑过期：返回旧值，后台异步重建
  -> Redis Key 不存在：Redisson 加锁，二次检查，再查 MySQL
  -> MySQL 不存在：缓存空字符串
```

### 3.1 Caffeine 本地缓存的创建

实现类：`src/main/java/com/hmdp/service/ShopCacheService.java`

```java
private final Cache<Long, Shop> localCache = Caffeine.newBuilder()
        // 单个 JVM 最多保存 10000 个店铺对象。
        .maximumSize(10_000)
        // 写入 5 分钟后本地数据自动失效，作为广播失败的最终兜底。
        .expireAfterWrite(5, TimeUnit.MINUTES)
        // 开启命中、未命中统计。
        .recordStats()
        .build();
```

Caffeine 是进程内缓存，速度快但不共享。部署三个应用实例，就有三份相互独立的 L1 数据。

### 3.2 BloomFilter 初始化

仍在 `ShopCacheService`：

```java
@EventListener(ApplicationReadyEvent.class)
@Scheduled(initialDelayString = "${hmdp.cache.bloom-retry-millis:30000}",
           fixedDelayString = "${hmdp.cache.bloom-retry-millis:30000}")
public void initializeBloomFilter() {
    if (bloomReady.get()) return;
    try {
        // 预计 10 万个 ID，误判率 1%。布隆过滤器允许误判，不允许漏判。
        shopIdBloomFilter.tryInit(100_000L, 0.01D);

        // 只查询 ID，避免加载完整店铺对象。
        List<Object> ids = shopMapper.selectObjs(
            new QueryWrapper<Shop>().select("id")
        );
        for (Object value : ids) {
            if (value instanceof Number) {
                shopIdBloomFilter.add(((Number) value).longValue());
            }
        }
        bloomReady.set(true);
    } catch (RuntimeException e) {
        // 初始化失败时不能继续使用未就绪 Bloom，否则可能把真实 ID 拒绝掉。
        // 此时降级为 Redis 空值缓存，并在 30 秒后重试初始化。
        bloomReady.set(false);
    }
}
```

### 3.3 店铺查询主方法

```java
public Shop queryById(Long id) {
    // 1. 先查 JVM 内的 Caffeine。
    Shop local = localCache.getIfPresent(id);
    if (local != null) {
        localHitCounter.increment();
        return local;
    }
    localMissCounter.increment();

    // 2. Bloom 明确判断不存在时，直接返回，不访问 Redis 和 MySQL。
    if (bloomReady.get() && !shopIdBloomFilter.contains(id)) {
        bloomRejectedCounter.increment();
        return null;
    }

    // 3. 查 Redis 逻辑过期缓存；必要时才回源 shopMapper.selectById。
    Shop shop = logicalExpireCacheClient.queryWithLogicalExpire(
        CACHE_SHOP_KEY,
        id,
        Shop.class,
        shopMapper::selectById,
        CACHE_SHOP_TTL,
        TimeUnit.MINUTES,
        CACHE_NULL_TTL,
        TimeUnit.MINUTES
    );

    // 4. Redis/MySQL 得到真实店铺后，回填 L1。
    if (shop != null) {
        localCache.put(id, shop);
    }
    return shop;
}
```

默认 Redis 店铺逻辑过期时间为 30 分钟，空值缓存为 2 分钟。

### 3.4 Redis 逻辑过期查询

实现类：`src/main/java/com/hmdp/utils/LogicalExpireCacheClient.java`

```java
public <ID, R> R queryWithLogicalExpire(
        String keyPrefix,
        ID id,
        Class<R> type,
        Function<ID, R> dbFallback,
        Long logicalExpireTime,
        TimeUnit logicalExpireUnit,
        Long nullExpireTime,
        TimeUnit nullExpireUnit) {

    String key = keyPrefix + id;
    String json = stringRedisTemplate.opsForValue().get(key);

    // 情况 1：Redis 中没有这个 Key。
    // 不能让所有请求直接查数据库，要进入互斥重建。
    if (json == null) {
        redisMissCounter.increment();
        return loadMissingWithMutex(
            key, id, type, dbFallback,
            logicalExpireTime, logicalExpireUnit,
            nullExpireTime, nullExpireUnit
        );
    }

    // 情况 2：命中空字符串，说明数据库中也不存在。
    if (StrUtil.isBlank(json)) {
        redisHitCounter.increment();
        return null;
    }

    RedisData redisData = JSONUtil.toBean(json, RedisData.class);
    R value = JSONUtil.toBean(
        JSONUtil.toJsonStr(redisData.getData()), type
    );

    // 情况 3：逻辑时间尚未过期，直接返回。
    if (redisData.getExpireTime().isAfter(LocalDateTime.now())) {
        redisHitCounter.increment();
        return value;
    }

    // 情况 4：逻辑过期。当前请求仍返回旧值，不等待数据库；
    // 只有抢到锁的后台线程负责重建。
    redisStaleCounter.increment();
    scheduleRebuild(
        key, id, dbFallback,
        logicalExpireTime, logicalExpireUnit,
        nullExpireTime, nullExpireUnit
    );
    return value;
}
```

逻辑过期数据的 Redis value 不是单独的 `Shop`，而是：

```json
{
  "data": {
    "id": 1,
    "name": "店铺名称"
  },
  "expireTime": "2026-09-08T12:30:00"
}
```

Redis Key 本身可以不物理过期，程序根据 `expireTime` 判断新旧。热点 Key 逻辑过期后仍可返回旧值，因此不会有大量请求同时等待数据库；代价是短时间内读到旧数据，属于可用性优先的最终一致方案。

### 3.5 冷缓存为什么要加锁并二次检查

```java
private <ID, R> R loadMissingWithMutex(
        String key,
        ID id,
        Class<R> type,
        Function<ID, R> dbFallback,
        Long logicalExpireTime,
        TimeUnit logicalExpireUnit,
        Long nullExpireTime,
        TimeUnit nullExpireUnit) {
    // 与更新店铺使用完全相同的锁 Key。
    RLock lock = redissonClient.getLock("lock:logical:" + key);
    boolean locked = false;
    try {
        // 最多等待 2 秒；拿到后租期 10 秒。
        locked = lock.tryLock(2, 10, TimeUnit.SECONDS);
        if (!locked) {
            throw new IllegalStateException("缓存正在重建，请稍后重试");
        }

        // 加锁前别的实例可能已经完成重建，所以必须二次检查 Redis。
        String latest = stringRedisTemplate.opsForValue().get(key);
        if (StrUtil.isNotBlank(latest)) {
            RedisData data = JSONUtil.toBean(latest, RedisData.class);
            return JSONUtil.toBean(JSONUtil.toJsonStr(data.getData()), type);
        }
        if (latest != null) {
            // latest 是空字符串，表示不存在。
            return null;
        }

        // 只有最终拿到锁且二次检查仍未命中的线程查询数据库。
        R value = dbFallback.apply(id);
        if (value == null) {
            // 空值使用较短物理 TTL，阻止恶意 ID 反复穿透数据库。
            stringRedisTemplate.opsForValue().set(
                key, "", jitteredSeconds(nullExpireUnit.toSeconds(nullExpireTime)),
                TimeUnit.SECONDS
            );
            return null;
        }

        setWithLogicalExpire(key, value,
                             logicalExpireTime, logicalExpireUnit);
        return value;
    } finally {
        if (locked && lock.isHeldByCurrentThread()) lock.unlock();
    }
}
```

“二次检查”不能省。假设 A、B 同时未命中，A 先获得锁并重建；B 随后得到锁时，如果不再查 Redis，就会重复访问 MySQL。

### 3.6 逻辑过期怎样异步重建

```java
private <ID, R> void scheduleRebuild(
        String key,
        ID id,
        Function<ID, R> dbFallback,
        Long logicalExpireTime,
        TimeUnit logicalExpireUnit,
        Long nullExpireTime,
        TimeUnit nullExpireUnit) {
    // 本 JVM 内先合并任务，同一个 key 只提交一个后台任务。
    if (!localRebuilding.add(key)) return;

    cacheRebuildExecutor.execute(() -> {
        RLock lock = redissonClient.getLock("lock:logical:" + key);
        boolean locked = false;
        try {
            // 不同 JVM 再通过 Redisson 竞争，最终只有一个实例回源数据库。
            locked = lock.tryLock();
            if (!locked) return;

            // 获锁后再次判断，防止其他实例已经重建完成。
            if (isNotExpired(stringRedisTemplate.opsForValue().get(key))) {
                return;
            }

            R latestValue = dbFallback.apply(id);
            if (latestValue == null) {
                // 数据已被删除，写空值缓存。
                long seconds = jitteredSeconds(
                    nullExpireUnit.toSeconds(nullExpireTime)
                );
                stringRedisTemplate.opsForValue().set(
                    key, "", seconds, TimeUnit.SECONDS
                );
            } else {
                setWithLogicalExpire(
                    key, latestValue,
                    logicalExpireTime, logicalExpireUnit
                );
            }
        } finally {
            if (locked && lock.isHeldByCurrentThread()) lock.unlock();
            localRebuilding.remove(key);
        }
    });
}
```

后台线程池在 `CacheConfig.cacheRebuildExecutor()` 中创建：核心线程 4、最大线程 8、队列 500。这样不会为每个过期请求无限创建线程。

### 3.7 随机过期怎样防缓存雪崩

```java
private long jitteredSeconds(long seconds) {
    long safeSeconds = Math.max(1L, seconds);
    long range = Math.max(1L, safeSeconds / 10L);

    // 在原 TTL 的 ±10% 区间内随机，让不同 Key 不在同一秒集中失效。
    return Math.max(
        1L,
        safeSeconds + ThreadLocalRandom.current().nextLong(-range, range + 1)
    );
}
```

这里随机的是逻辑过期时间；空值缓存随机的是 Redis 物理 TTL。

### 3.8 更新店铺后怎样保证多实例缓存一致

实现类：`src/main/java/com/hmdp/service/impl/ShopServiceImpl.java`

```java
@Override
@Transactional
public Result update(Shop shop) {
    if (shop.getId() == null) {
        return Result.fail("店铺id不能为空");
    }

    // 与缓存重建使用同一把锁。
    // 这样更新期间不会有旧查询把旧数据库值重新写入 Redis。
    RLock writeLock = shopCacheService.getWriteLock(shop.getId());
    writeLock.lock();
    boolean callbackRegistered = false;
    try {
        if (!updateById(shop)) {
            return Result.fail("店铺不存在或更新失败");
        }

        TransactionSynchronizationManager.registerSynchronization(
            new TransactionSynchronization() {
                @Override
                public void afterCommit() {
                    // 只有数据库真正提交成功才删除缓存。
                    shopCacheService.evictAndBroadcast(shop.getId());
                }

                @Override
                public void afterCompletion(int status) {
                    // 一直持锁到事务提交或回滚完成。
                    if (writeLock.isHeldByCurrentThread()) {
                        writeLock.unlock();
                    }
                }
            }
        );
        callbackRegistered = true;
        return Result.ok();
    } finally {
        if (!callbackRegistered && writeLock.isHeldByCurrentThread()) {
            writeLock.unlock();
        }
    }
}
```

缓存删除和广播在 `ShopCacheService.evictAndBroadcast()`：

```java
public void evictAndBroadcast(Long shopId) {
    // 当前实例 L1。
    localCache.invalidate(shopId);

    // 所有实例共享的 L2。
    stringRedisTemplate.delete(CACHE_SHOP_KEY + shopId);

    // 新增店铺时，把新 ID 加入 BloomFilter。
    shopIdBloomFilter.add(shopId);

    // 通知其他实例删除各自的 L1。
    invalidationPublisher.publishShopInvalidation(shopId);
}
```

RabbitMQ 使用 Fanout Exchange，每个实例声明自己的匿名队列：


生产者：

消费者：


广播失败时，当前实例 L1 和共享 Redis L2 已删除；其他实例最迟在 Caffeine 的 5 分钟 TTL 到期后自然收敛。

### 3.9 三种缓存问题分别由谁处理

| 问题 | 当前代码方案 | 实现位置 |
|---|---|---|
| 缓存穿透 | BloomFilter + 空值缓存 | `ShopCacheService`、`LogicalExpireCacheClient` |
| 缓存击穿 | 逻辑过期返回旧值 + Redisson 互斥异步重建；冷 Key 互斥加载 | `LogicalExpireCacheClient` |
| 缓存雪崩 | 逻辑过期时间和空值 TTL 加 ±10% 随机抖动 | `jitteredSeconds()` |
| 多实例 L1 不一致 | 更新提交后 RabbitMQ Fanout 广播删除 | `CacheInvalidationPublisher/Consumer` |
| 更新与重建并发 | 写操作与缓存重建使用同一个 Redisson 锁 | `ShopServiceImpl`、`LogicalExpireCacheClient` |

## 4. Redisson 分布式锁具体怎样使用

### 4.1 RedissonClient 的创建

实现类：`src/main/java/com/hmdp/config/RedissonConfig.java`

```java
@Configuration
public class RedissonConfig {

    @Bean(destroyMethod = "shutdown")
    public RedissonClient redissonClient(RedisProperties redisProperties) {
        Config config = new Config();
        SingleServerConfig server = config.useSingleServer()
                .setAddress(
                    "redis://" + redisProperties.getHost()
                    + ":" + redisProperties.getPort()
                )
                .setDatabase(redisProperties.getDatabase());

        if (StringUtils.hasText(redisProperties.getPassword())) {
            server.setPassword(redisProperties.getPassword());
        }
        return Redisson.create(config);
    }
}
```

业务类注入 `RedissonClient` 后，通过 `getLock(lockKey)` 获得 `RLock`。

### 4.2 当前项目的三类锁

| 锁 Key | 使用位置 | 锁住的资源 | 解决的问题 |
|---|---|---|---|
| `lock:order:{userId}:{voucherId}` | `VoucherOrderConsumer` | 某用户购买某张券 | 减少重复下单并发竞争 |
| `lock:seckill:lifecycle:{orderId}` | 消费者、恢复任务、死信消费者 | 一笔订单的生命周期 | 防止建单和最终补偿同时发生 |
| `lock:logical:cache:shop:{shopId}` | 缓存重建、店铺更新 | 某店铺缓存 | 防缓存击穿、防旧值回写 |

锁粒度不能写成一个全局 `lock:order`。那样所有用户、所有券都会串行，高并发能力会被锁直接抹掉。

### 4.3 `tryLock()` 和 `lock()` 的选择

秒杀消费者使用：

```java
if (!lifecycleLock.tryLock()) {
    throw new IllegalStateException("获取锁失败");
}
```

获取失败立即抛异常，让 RabbitMQ 重试，不让消费线程长期阻塞。

冷缓存重建使用：

```java
lock.tryLock(2, 10, TimeUnit.SECONDS);
```

最多等 2 秒，拿到后租期 10 秒，避免请求无限堆积。

店铺更新使用：

```java
writeLock.lock();
```

更新必须与缓存重建互斥，而且锁要一直持有到数据库事务结束，所以允许等待并由 Redisson 看门狗自动续期。

### 4.4 解锁为什么总要放在 `finally`

```java
RLock lock = redissonClient.getLock(lockKey);
boolean locked = lock.tryLock();
try {
    if (!locked) {
        throw new IllegalStateException("获取锁失败");
    }
    // 业务代码
} finally {
    // 只允许持锁线程释放，避免异常路径误解锁。
    if (locked && lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

Redisson 默认锁支持可重入，并在未指定固定租期的 `lock()`/`tryLock()` 场景启用看门狗续期。应用崩溃后续期停止，锁会在租约到期后释放；正常执行必须在 `finally` 主动解锁。
